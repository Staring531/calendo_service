# 软件开发流程规范 V1.0

**文档编号：** MEMREPO-DEV-STD-001  
**版本：** V1.0  
**状态：** 初始基线  
**适用项目：** memrepo  
**开发组织：** 个人开发者 + Cursor AI  
**代码托管：** GitHub  
**包管理工具：** pnpm  

---

## 1. 文档目的

本规范用于定义 memrepo 软件项目从需求提出到最终交付的完整开发流程，建立统一、可执行、可追溯、可验证的工程管理机制。

本规范重点解决以下问题：

1. 需求与最终实现之间缺乏追溯关系。
2. AI 辅助开发过程中出现未经批准的需求扩张。
3. 技术方案和代码修改缺少事实依据。
4. AI 生成代码、测试和测试报告后自行宣布完成，缺少有效验证。
5. 开发过程、变更过程和测试过程缺少完整记录。
6. 项目逐渐偏离原有需求、技术决策和架构约束。
7. 最终交付无法明确说明实现了什么、验证了什么以及遗留了什么。

本规范建立以需求追溯、变更控制、证据验证和交付闭环为核心的开发管理体系。

本规范不以文档数量、流程形式或采用某种开发方法论作为质量标准。所有过程要求均应服务于实际开发质量和风险控制。

## 2. 适用范围

本规范适用于 memrepo 项目的：

- 项目初始化；
- 需求管理；
- 技术调查；
- 技术方案设计；
- 架构设计；
- 任务拆分；
- AI 辅助代码实现；
- 代码变更管理；
- 软件测试；
- 质量验证；
- 代码审查；
- 版本交付；
- 缺陷处理；
- 技术债务管理；
- 开发流程改进。

本规范适用于个人开发者使用 Cursor AI 完成开发工作的场景。

当项目规模、开发组织或技术环境发生变化时，应重新评估本规范的适用性。

## 3. 开发组织与职责

### 3.1 组织模式

memrepo 采用个人开发者主导、Cursor AI 辅助执行的开发模式。

开发者同时承担：

- 产品需求提出者；
- 需求确认者；
- 技术决策者；
- 开发负责人；
- 变更批准者；
- 最终验收者。

Cursor AI 作为辅助开发工具，负责在授权范围内执行调查、分析、计划、代码实现、测试辅助和问题定位。

GitHub 负责保存需求、变更、提交、审查和交付记录。

自动化检查负责提供可重复执行的技术验证结果。

### 3.2 职责分工

| 工作事项 | 开发者 | Cursor AI | GitHub / CI |
|---|---|---|---|
| 需求提出 | 负责 | 协助 | 保存记录 |
| 需求澄清 | 最终确认 | 分析和提问 | 保存记录 |
| 技术调查 | 审查结论 | 执行调查 | 保存证据链接 |
| 技术决策 | 最终批准 | 提供方案 | 保存决策 |
| 实施计划 | 审核批准 | 编制计划 | 关联任务 |
| 代码实现 | 监督和控制 | 按授权执行 | 保存版本 |
| 测试编写 | 确认要求 | 协助编写 | 保存代码 |
| 自动化验证 | 检查结果 | 协助分析 | 执行检查 |
| 最终验收 | 唯一责任人 | 提供材料 | 保存交付记录 |

### 3.3 权限原则

以下事项必须由开发者决定：

1. 需求范围的确认和变更。
2. 重要技术方案的选择。
3. 架构边界和关键数据结构的变更。
4. 依赖引入、删除或重要版本升级。
5. 高风险代码变更的批准。
6. 生产数据和部署环境操作。
7. 最终验收和交付确认。

Cursor AI 不得自行批准其提出的需求变更、技术决策或最终交付。

Cursor AI 的自我审查不能替代开发者验收，也不能替代自动化验证。

## 4. 核心工程原则

### 4.1 事实优先原则

所有影响需求、架构、实现和测试的重要结论，都必须有相应依据。

依据可以包括：

- 项目源代码；
- 项目配置；
- 实际执行结果；
- 自动化测试结果；
- 官方技术文档；
- 正式技术标准；
- 经确认的需求记录；
- 经批准的技术决策。

不得将推测、经验判断或 AI 生成内容直接描述为已验证事实。

### 4.2 需求驱动原则

每项正式开发工作必须有明确的需求、缺陷或维护任务来源。

不得仅因为 AI 提出某项改进建议，就直接将其作为已批准的开发任务。

### 4.3 调查先于实现原则

涉及现有代码、技术选型、依赖、接口或架构的任务，必须先完成必要调查，再进入实现阶段。

调查结果不足以支持实现时，应继续调查或向开发者提出问题。

### 4.4 变更可控原则

所有代码修改必须具有明确目的和范围。

不得未经批准扩大需求范围、擅自重构无关模块或改变既定技术决策。

### 4.5 验证独立原则

实现完成不等于验证通过。

AI 的文字报告不能替代实际命令执行结果、自动化检查记录和开发者验收。

### 4.6 过程可追溯原则

重要开发活动必须保留可检查的记录，使需求、方案、实现、测试和交付之间建立关联。

### 4.7 最小必要原则

流程记录和工程文档应与任务复杂度相适应。

简单任务可以采用简化流程，不得为了形式完整而制造无实际用途的文档。

### 4.8 持续改进原则

开发流程不是固定不变的。应通过真实任务试运行、缺陷分析和开发反馈持续修订。

## 5. 开发生命周期

memrepo 采用以下开发生命周期：

1. 项目基线管理；
2. 需求管理；
3. 调查与分析；
4. 设计与计划；
5. 实现与变更控制；
6. 测试与验证；
7. 审查与交付；
8. 维护与持续改进。

每个阶段必须明确输入、执行要求、输出和完成条件。

### 5.1 项目基线管理

**目的：** 建立项目统一的目标、范围、技术约束和工程要求。

主要活动：

- 明确项目目标；
- 明确项目边界；
- 确认开发工具；
- 确认技术环境；
- 定义质量要求；
- 建立项目级工程规范；
- 建立必要的仓库管理规则。

主要输出：

- 项目说明；
- 项目约束；
- 工程流程规范；
- 项目级开发规则；
- 技术环境基线。

完成条件：

- 项目目标和范围已经确认；
- 已知约束已记录；
- 未确定事项已明确标注；
- 开发流程已经批准。

### 5.2 需求管理

**目的：** 确保每项开发工作具有明确、可理解、可验证的需求依据。

#### 5.2.1 需求来源

需求可以来自：

- 开发者提出的新功能；
- 用户反馈；
- 缺陷修复；
- 技术改进；
- 性能优化；
- 安全改进；
- 维护和兼容性要求。

#### 5.2.2 需求记录

每项正式需求原则上通过 GitHub Issue 管理。

需求记录至少包含：

| 字段 | 内容 |
|---|---|
| 需求编号 | GitHub Issue 编号 |
| 需求标题 | 简明描述 |
| 需求来源 | 需求提出者或发现渠道 |
| 原始描述 | 尽量保留需求原意 |
| 目标 | 解决什么问题 |
| 功能范围 | 本次需要完成什么 |
| 非目标 | 本次明确不处理什么 |
| 验收条件 | 如何判断需求满足 |
| 约束条件 | 技术、业务、性能、安全等约束 |
| 待确认问题 | 尚未解决的问题 |
| 当前状态 | 需求处理状态 |

#### 5.2.3 需求澄清

Cursor AI 可以：

- 分析需求歧义；
- 提出澄清问题；
- 识别需求冲突；
- 识别遗漏的边界条件；
- 协助编写验收条件。

Cursor AI 不得自行将未经确认的内容写成正式需求。

对于无法确定的事项，必须标记为待确认。

#### 5.2.4 需求变更

需求确认后发生变化时，必须记录：

- 原需求；
- 变更内容；
- 变更原因；
- 影响范围；
- 对现有设计和实现的影响；
- 对测试和交付的影响；
- 开发者确认结果。

未经确认的需求变更不得直接进入实现。

### 5.3 调查与分析

**目的：** 为技术设计和代码实现建立事实依据。

调查内容根据任务类型确定，包括：

- 现有代码结构；
- 模块职责；
- 数据流和调用关系；
- 配置和依赖；
- 已有测试；
- 官方技术资料；
- 兼容性要求；
- 安全和性能限制；
- 外部服务能力。

#### 5.3.1 调查要求

Cursor AI 应先调查，再提出结论。

调查报告应区分：

| 类型 | 定义 |
|---|---|
| 已验证事实 | 有直接证据支持 |
| 官方资料 | 来自官方文档或正式标准 |
| 实验结果 | 通过实际操作或命令得到 |
| 分析推论 | 根据现有事实推导 |
| 未知项 | 目前无法确认 |
| 待决问题 | 需要开发者作出决定 |

对于代码事实，尽可能提供文件路径、符号名称和相关代码位置。

对于外部技术事实，尽可能提供官方资料链接及其适用版本。

对于运行结果，应提供实际执行的命令及结果。

#### 5.3.2 调查边界

调查阶段默认不修改项目代码和配置。

如果调查必须进行实验性修改，应先说明目的、修改范围和恢复方式，并取得开发者同意。

#### 5.3.3 调查完成条件

- 关键事实已经核实；
- 相关风险已经识别；
- 未知项已经明确；
- 调查结论有相应证据；
- 调查结果足以支持方案设计，或明确指出尚不能继续的原因。

### 5.4 设计与计划

**目的：** 在实现前明确解决方案、实施范围和验证方式。

#### 5.4.1 方案设计

对于需要技术设计的任务，应说明：

- 目标；
- 设计思路；
- 涉及模块；
- 关键接口；
- 数据结构；
- 依赖变化；
- 备选方案；
- 选择依据；
- 风险；
- 兼容性影响；
- 验证方式。

简单任务可以直接在 Issue 中记录方案。

中等任务应提供清晰的实施计划。

大型任务或重大架构变更应形成独立设计文档。

#### 5.4.2 技术决策记录

对于具有长期影响的技术决策，采用 ADR（Architecture Decision Record）记录。

ADR 至少包含：

- 决策编号；
- 决策标题；
- 背景；
- 需要解决的问题；
- 候选方案；
- 选择的方案；
- 选择理由；
- 影响；
- 状态；
- 关联需求或任务。

不是每个小技术选择都需要 ADR。

#### 5.4.3 实施计划

实施计划应包含：

- 任务拆分；
- 实施顺序；
- 预期修改文件或模块；
- 关键实现步骤；
- 需要新增或修改的测试；
- 验证命令或验证方式；
- 风险及处理方法。

实施计划必须由开发者确认后才能进入实现。

### 5.5 实现与变更控制

**目的：** 确保代码实现严格遵循批准的需求和设计。

#### 5.5.1 实现要求

Cursor AI 必须：

1. 阅读相关代码和配置。
2. 确认当前工作区状态。
3. 遵循已批准的实施计划。
4. 按照合理的小任务逐步修改。
5. 避免无关重构。
6. 保持现有功能和接口兼容，除非需求明确允许变更。
7. 为新增行为提供适当测试。
8. 修改后检查 Git diff。
9. 报告实际修改内容。
10. 报告未完成事项和风险。

#### 5.5.2 变更范围

实施前应明确：

- 本次允许修改的模块；
- 可能受到影响的模块；
- 不应修改的范围；
- 是否允许新增依赖；
- 是否允许修改公开接口；
- 是否允许修改数据结构；
- 是否涉及数据库或外部服务。

#### 5.5.3 超范围变更

如果实施中发现原计划无法满足需求，或需要扩大修改范围，Cursor AI 必须：

1. 暂停相关扩展修改；
2. 说明发现的问题；
3. 提供证据；
4. 分析影响；
5. 提出可选方案；
6. 等待开发者确认；
7. 更新需求或实施计划；
8. 再继续实施。

#### 5.5.4 Git 变更记录

重要修改必须通过 Git 保存。

每项开发任务原则上使用独立短生命周期分支。

分支命名建议：

- `feat/<issue-id>-<short-name>`
- `fix/<issue-id>-<short-name>`
- `chore/<issue-id>-<short-name>`
- `docs/<issue-id>-<short-name>`

提交信息应说明修改目的，并尽可能关联 Issue。

实现前后检查：

```bash
git status --short
git diff --stat
git diff
```

不得将未经检查的无关修改混入任务提交。

### 5.6 测试与验证

**目的：** 证明实现满足规定的质量要求和需求验收条件。

#### 5.6.1 验证层级

根据技术架构和任务风险选择必要的验证方式。

| 层级 | 验证内容 |
|---|---|
| 静态检查 | 格式、类型、静态分析 |
| 单元测试 | 独立函数和模块逻辑 |
| 集成测试 | 模块之间的协作 |
| 端到端测试 | 完整用户场景 |
| 手工验证 | 自动化难以覆盖的实际行为 |
| 安全验证 | 与任务风险相关的安全要求 |
| 性能验证 | 有明确性能目标时执行 |

不得为了满足形式而强制所有任务执行不适用的测试。

#### 5.6.2 测试设计

测试应尽量与需求验收条件建立关联。

对于重要业务规则，应优先考虑自动化测试。

对于缺陷修复，应尽可能增加能够复现原问题的回归测试。

对于高风险变更，应增加必要的集成、兼容性或实际运行验证。

#### 5.6.3 测试记录

测试记录至少包括：

- 对应需求；
- 验证对象；
- 测试环境；
- 执行命令；
- 预期结果；
- 实际结果；
- 执行状态；
- 失败信息；
- 证据位置。

测试状态必须区分：

- PASS：已执行并通过；
- FAIL：已执行但失败；
- NOT RUN：未执行；
- BLOCKED：因条件不足无法执行；
- PARTIAL：仅完成部分验证。

不得将未执行的测试描述为通过。

#### 5.6.4 测试结果的可信度

测试报告必须来源于实际执行结果。

Cursor AI 可以执行测试、解释输出和协助定位问题，但不得编造测试结果。

GitHub Actions 的执行结果作为自动化检查的主要记录依据。

### 5.7 审查与交付

**目的：** 确保最终交付满足需求和质量要求。

#### 5.7.1 Pull Request

正式功能、缺陷修复和重要维护任务原则上通过 GitHub Pull Request 合并。

PR 必须关联对应 Issue，并记录：

- 变更目的；
- 变更内容；
- 修改范围；
- 重要技术决策；
- 测试和验证结果；
- 验收条件检查情况；
- 已知问题；
- 遗留事项。

#### 5.7.2 单人审查

由于开发者是唯一开发和验收人员，不要求开发者批准自己创建的 PR。

PR 用于集中记录变更和执行审查。

开发者必须实际检查：

- 变更是否符合需求；
- 是否出现未经批准的修改；
- 是否存在无关重构；
- 是否引入不必要的依赖；
- 是否影响已有功能；
- 测试是否真实执行；
- 测试是否覆盖关键场景；
- 是否存在安全或兼容性风险；
- 文档是否需要同步更新。

Cursor 的二次审查可以作为辅助，但不能代替开发者的最终判断。

#### 5.7.3 合并与交付

满足规定的质量门槛后，开发者可以合并 PR。

合并后应确认：

- Issue 已正确关联；
- 代码已进入主分支；
- CI 检查结果符合要求；
- 必要文档已更新；
- 遗留问题已记录。

正式版本发布时，应根据项目实际需要建立 GitHub Release。

### 5.8 维护与持续改进

交付后发现的问题应重新进入需求或缺陷管理流程。

缺陷记录至少包括：

- 现象；
- 复现条件；
- 影响范围；
- 严重程度；
- 根因（确认后记录）；
- 修复方案；
- 回归验证。

不得仅通过修改代码而不记录重要缺陷的原因和影响。

流程改进应基于真实问题和实际证据，不得为了增加流程复杂度而修改规范。

## 6. 开发任务状态管理

每项任务应具有明确状态。

建议状态：

1. Backlog：待处理；
2. Clarifying：需求澄清；
3. Investigating：调查中；
4. Designing：设计中；
5. Ready：允许实现；
6. In Progress：实现中；
7. Verifying：验证中；
8. Accepted：验收通过；
9. Done：已交付；
10. Blocked：阻塞；
11. Rejected：不再处理。

状态变化必须符合实际工作情况。

不得因为 Cursor 声称完成就直接把任务标记为 Done。

任务被阻塞时，应记录原因和解除条件。

## 7. 任务准入与完成标准

### 7.1 Definition of Ready（DoR）

任务满足以下条件后，才能进入实现阶段：

- 需求目标明确；
- 功能范围明确；
- 非目标明确；
- 关键验收条件明确；
- 重要技术事实已经调查；
- 关键未知项已解决或有明确处理方案；
- 重要技术决策已获批准；
- 实施计划已确认；
- 修改边界已明确；
- 验证方式已确定。

不满足条件时，任务不得进入正式实现。

### 7.2 Definition of Done（DoD）

任务满足以下条件后，才能标记为已交付：

- 批准的需求已经实现；
- 没有未经批准的范围扩张；
- 重要变更有明确记录；
- 规定的测试已经执行；
- 规定的测试达到预期结果；
- 关键验收条件有验证证据；
- Git diff 已检查；
- PR 记录完整；
- CI 结果符合要求；
- 必要文档已更新；
- 已知问题和遗留事项已记录；
- 开发者已经完成最终验收。

CI 通过不自动代表需求验收通过。

## 8. 风险分级与流程强度

根据任务影响和失败后果确定流程强度。

### 8.1 低风险任务

例如：

- 文档修正；
- 注释修正；
- 不影响行为的小型维护；
- 简单配置调整。

可以采用简化调查和计划，但仍必须检查变更。

### 8.2 中风险任务

例如：

- 新增业务功能；
- 修改已有模块逻辑；
- 调整模块接口；
- 新增依赖；
- 修改重要配置。

必须执行完整的需求、调查、计划、实现、测试和 PR 审查流程。

### 8.3 高风险任务

例如：

- 数据库结构和数据迁移；
- 身份认证和权限控制；
- 敏感数据处理；
- 安全边界变更；
- 重大架构调整；
- 生产环境部署；
- 可能造成数据丢失的操作。

必须增加：

- 更详细的影响分析；
- 备份和恢复方案；
- 回滚方案；
- 更充分的测试；
- 开发者明确批准；
- 必要时的外部专业审查。

风险等级应由实际影响决定，不得仅根据代码修改量判断。

## 9. Cursor AI 使用规范

### 9.1 工作模式

| 工作阶段 | 推荐模式 | 项目修改权限 |
|---|---|---|
| 需求分析 | Ask | 不允许 |
| 代码调查 | Ask | 不允许 |
| 技术研究 | Ask | 不允许 |
| 实施计划 | Plan | 先批准后执行 |
| 代码实现 | Agent | 限定范围内允许 |
| 测试修复 | Agent | 限定范围内允许 |
| 最终审查 | 新的 Ask 对话 | 不允许 |

具体模式名称和权限行为应以当前安装版本的 Cursor 官方文档及实际设置为准。

### 9.2 AI 行为要求

Cursor AI 必须遵循：

1. 不得编造代码、接口、配置或技术能力。
2. 不得编造命令执行和测试结果。
3. 不得把推测当作事实。
4. 不得擅自修改需求。
5. 不得未经批准扩大修改范围。
6. 不得为了通过测试而删除有效测试。
7. 不得擅自升级、替换或引入重要依赖。
8. 不得擅自进行无关重构。
9. 修改前必须理解相关代码。
10. 修改后必须检查差异。
11. 测试失败时必须如实报告。
12. 未验证事项必须明确标记。
13. 不得将 AI 自我审查描述为独立人工审查。

### 9.3 高风险操作

以下操作必须经过开发者明确批准：

- 删除大量文件或目录；
- 大规模代码重构；
- 数据库迁移和数据删除；
- 修改生产环境；
- 部署和发布；
- 强制推送或重写 Git 历史；
- 修改仓库权限和安全配置；
- 处理凭据和敏感数据；
- 变更 CI 权限；
- 其他可能产生不可逆影响的操作。

AI 执行权限应根据实际风险设置，不应默认开放完全自动执行。

## 10. GitHub 管理规范

### 10.1 GitHub 对象职责

| 对象 | 主要职责 |
|---|---|
| Issue | 需求、缺陷、技术任务 |
| Pull Request | 变更审查和验收记录 |
| Actions | 自动化检查和测试 |
| Releases | 正式版本发布记录 |
| Projects | 跨任务规划，按需使用 |
| Discussions | 长期讨论，按需使用 |

### 10.2 分支策略

采用以 main 为稳定主线的短生命周期分支策略。

建议分支：

- `main`
- `feat/*`
- `fix/*`
- `chore/*`
- `docs/*`

初始阶段不强制采用复杂的 GitFlow 或多级长期分支。

### 10.3 主分支保护

在 GitHub 套餐和仓库设置支持的前提下，应逐步启用：

- 限制直接推送；
- 禁止强制推送；
- 禁止删除主分支；
- 要求规定的 CI 检查通过；
- 通过 PR 进行变更审查。

由于项目采用单人开发模式，不要求另一个人的 PR 审批。

### 10.4 记录关联

正式开发任务应建立 Issue 与 PR 的关联。

PR 描述应包含对应 Issue 编号。

建议使用 GitHub 支持的自动关闭关键词，例如：

`Closes #123`

## 11. pnpm 工程管理规范

pnpm 用于管理项目依赖、工作区和工程命令，不承担需求或开发过程管理职责。

要求：

1. 固定并记录 Node.js 和 pnpm 版本。
2. 使用 Git 管理 `package.json`。
3. 使用 Git 管理 `pnpm-lock.yaml`。
4. 依赖变化必须审查清单和锁文件差异。
5. CI 使用冻结锁文件安装。
6. 实际项目脚本必须根据技术栈确定。
7. 不得假设项目已经存在某个测试、构建或检查脚本。
8. 是否采用 pnpm Workspace，应由实际架构决定。

推荐 CI 安装命令：

```bash
pnpm install --frozen-lockfile
```

如果未来需要多个独立包或多个应用，再根据实际需要引入 `pnpm-workspace.yaml`。

## 12. 文档与记录管理

### 12.1 记录原则

文档应当用于保存：

- 项目事实；
- 需求；
- 技术决策；
- 调查结论；
- 重要变更；
- 验证结果；
- 交付信息。

不应把每次 AI 对话全文复制到仓库作为正式开发记录。

### 12.2 记录位置

| 内容 | 推荐记录位置 |
|---|---|
| 用户需求 | GitHub Issue |
| 需求讨论和变更 | GitHub Issue |
| 技术调查 | Issue 或 `docs/investigations/` |
| 重要技术决策 | `docs/decisions/` |
| 项目架构 | `docs/architecture/` |
| 代码修改 | Git Commit / PR |
| 自动化验证 | GitHub Actions |
| 最终验收 | PR |
| 版本交付 | GitHub Release |

### 12.3 文档维护

文档与实际代码不一致时，应根据实际事实修订文档。

重要技术决策被替代时，应更新其状态并记录新的决策依据。

不得将已经失效的技术方案继续作为当前项目约束。

## 13. 证据管理规范

重要工程结论应有对应证据。

证据应满足：

- 来源明确；
- 内容可检查；
- 与结论相关；
- 时间和版本信息必要时可识别；
- 不夸大其能够证明的范围。

证据类型包括：

1. 需求记录；
2. 代码和配置；
3. Git 提交及差异；
4. 官方技术文档；
5. 命令执行输出；
6. 测试报告；
7. CI 运行结果；
8. 人工验收记录。

应明确区分：

- 证据证明的事实；
- 根据事实得到的推论；
- 尚未验证的假设；
- 仍需开发者决定的问题。

不得将搜索摘要、AI 生成的解释或未经检查的测试报告当作充分证据。

## 14. 异常处理

### 14.1 需求不明确

暂停实现，提出具体澄清问题，等待开发者确认。

### 14.2 调查证据不足

继续调查，或者明确说明当前无法得出结论的原因。

### 14.3 方案不可行

说明事实依据、失败原因、影响范围和替代方案，等待重新决策。

### 14.4 实现超出范围

暂停额外修改，报告原因，取得批准后更新实施计划。

### 14.5 测试失败

记录失败命令、实际输出、影响范围和定位结果。

不得删除有效测试或降低验收标准来掩盖失败。

### 14.6 CI 失败

不得将任务标记为已交付。

修复失败原因后重新执行相关检查。

### 14.7 发现重大风险

暂停相关操作，评估数据、代码、环境和交付影响，制定恢复方案后再继续。

### 14.8 任务取消

记录取消原因、已完成工作、遗留修改和需要恢复的内容。

## 15. 流程质量度量

初期采用以下指标观察流程质量：

| 指标 | 计算或检查方法 |
|---|---|
| 需求追溯率 | 可关联明确需求的交付变更 / 全部交付变更 |
| 验收覆盖率 | 有验证证据的验收条件 / 全部验收条件 |
| 变更可解释率 | 有明确原因的变更 / 全部重要变更 |
| 未授权范围变更数 | 未经确认的范围扩张次数 |
| 验证执行率 | 实际执行的规定检查 / 全部规定检查 |
| 交付后缺陷 | 交付后发现的缺陷数量和严重程度 |
| 流程执行成本 | 单个任务投入的流程时间 |

初期不设定未经验证的硬性数值目标。

应通过实际任务积累基线，再确定合理的改进目标。

## 16. 工程流程实施顺序

本规范通过以下阶段实施：

### 第一阶段：流程基线建立

- 确认项目目标和范围；
- 确认工程流程；
- 确认职责和权限；
- 确认质量门槛；
- 确认记录要求。

### 第二阶段：工具配置

- 配置 GitHub 仓库管理规则；
- 创建 Issue 模板；
- 创建 PR 模板；
- 配置 Cursor 项目规则；
- 配置基础 CI；
- 建立依赖管理约束。

### 第三阶段：项目初始化

- 确认技术栈；
- 初始化 pnpm 工程；
- 建立必要目录；
- 配置基础检查和测试；
- 验证开发环境。

### 第四阶段：流程试运行

选择一个真实、范围较小的需求，完整执行需求、调查、设计、实现、测试、审查和交付流程。

### 第五阶段：流程修订

根据试运行结果识别：

- 不必要的流程步骤；
- 缺少的质量控制；
- Cursor 执行偏差；
- 记录成本过高的环节；
- 自动化不足的环节。

修订后形成下一版本规范。

## 17. 规范变更管理

本规范本身属于受控工程文档。

规范发生变更时，应记录：

- 变更原因；
- 变更内容；
- 影响范围；
- 与现有规则的兼容性；
- 变更后的执行要求；
- 批准结果。

不得在没有说明的情况下随意修改核心质量要求。

规范修订应通过 Git 进行版本管理。

建议采用以下版本规则：

- 主版本：开发流程、职责或核心控制机制发生重大变化；
- 次版本：增加或调整重要流程要求；
- 修订版本：文字修正和不改变规范含义的澄清。

## 18. 当前未确定事项

由于 memrepo 当前为空仓库，以下事项不属于本版本已经确认的技术事实，必须在项目初始化阶段进一步确定：

1. memrepo 的具体产品目标和功能范围；
2. 目标运行环境；
3. Node.js 版本；
4. pnpm 版本；
5. TypeScript 或 JavaScript 的选择；
6. 应用框架；
7. 测试框架；
8. 静态检查工具；
9. 构建工具；
10. 是否采用 pnpm Workspace；
11. 数据存储方案；
12. 部署方式；
13. 安全和性能目标；
14. CI 所需的具体命令和工作流。

在上述事项确定之前，不得将示例配置、示例目录或示例命令描述为项目已经具备的能力。

## 19. 规范生效与执行

本规范作为 memrepo 第一版软件开发流程基线。

项目初始化、工具配置和后续开发均应遵循本规范。

对于尚未确定的技术细节，应通过项目调查、技术决策和后续规范修订逐步补齐。

本规范的有效性以实际开发任务的执行效果、证据完整性、变更可控性和交付质量为判断依据，而不是以文档是否全部编写完成为判断依据。
