# 流程规范 V1.0 落地实施清单

## 1. 实施目标

将《memrepo 软件开发流程规范 V1.0》转换为实际可执行的工程管理机制。

实施时遵循以下原则：

- 先建立必要的管理机制，再建立自动化能力。
- 不提前假设项目技术栈和运行环境。
- 每项流程要求都应有对应的执行方式和验证依据。
- 自动化无法覆盖的事项，明确由开发者人工执行。
- 不为了形式完整而引入不必要的工具和配置。

## 2. 实施状态定义

| 状态 | 含义 |
|---|---|
| 未开始 | 尚未实施 |
| 调查中 | 正在确认实施方式或工具能力 |
| 待实施 | 实施方案已明确 |
| 实施中 | 正在配置或执行 |
| 已完成 | 已实施且通过验证 |
| 暂缓 | 当前不具备实施条件或暂时没有必要 |
| 不适用 | 经确认不适用于当前项目 |

## 3. 第一阶段：项目管理基础

目标：建立需求、任务、变更和交付的基本管理机制。

| 编号 | 实施事项 | 实施方式 | 验证依据 |
|---|---|---|---|
| P-01 | 确定 GitHub 仓库作为项目管理和代码托管入口 | 检查仓库及访问权限 | 仓库可正常访问 |
| P-02 | 建立 Issue 管理规则 | 定义 Issue 类型、标题和内容要求 | 可以通过 Issue 描述需求和缺陷 |
| P-03 | 建立任务状态管理规则 | 定义状态及状态转换条件 | 任务状态能够反映实际进度 |
| P-04 | 建立需求验收标准 | 要求需求记录验收条件 | 需求具备可验证的完成条件 |
| P-05 | 建立变更管理规则 | 通过 Issue、PR 和提交记录关联变更 | 能追溯变更原因和实施结果 |
| P-06 | 建立 PR 说明规则 | 记录变更内容、关联任务和验证结果 | PR 能够说明变更及其验证情况 |
| P-07 | 建立版本管理规则 | 确定版本发布和变更记录方式 | 可以追溯正式版本 |

**阶段完成条件：**

- 需求有统一记录入口。
- 任务有明确状态。
- 需求、代码变更和交付结果能够关联。
- 不要求为了单人开发而强制设置第二人审批。

## 4. 第二阶段：Cursor AI 协作机制

目标：明确 Cursor AI 在需求分析、计划、实现和审查中的工作边界。

| 编号 | 实施事项 | 实施方式 | 验证依据 |
|---|---|---|---|
| C-01 | 建立项目级 Cursor Rules | 将通用项目规则写入项目配置 | Cursor 能读取项目规则 |
| C-02 | 定义调查阶段工作要求 | 明确先检查现状、再提出结论 | 调查结果包含事实和证据 |
| C-03 | 定义计划阶段工作要求 | 要求列出范围、步骤、风险和验证方法 | 计划可以供用户审查 |
| C-04 | 定义实现阶段工作要求 | 限定修改范围，禁止未经批准扩展需求 | 实际 diff 与批准范围一致 |
| C-05 | 定义验证阶段工作要求 | 要求报告测试命令、结果和未验证事项 | 验证报告可以复核 |
| C-06 | 定义 AI 不得自行批准的事项 | 明确需求、重大方案、重要变更和最终验收由用户决定 | 关键决策有用户确认记录 |
| C-07 | 建立 AI 结论的证据要求 | 区分事实、推论、未知和待验证事项 | 结论有可追溯依据 |

**阶段完成条件：**

- Cursor 有明确的项目级行为规则。
- 调查、计划、实现、验证具有不同的工作边界。
- AI 不会将自己的推断表述为已经验证的事实。
- 重要决策保留用户批准记录。

## 5. 第三阶段：代码仓库与工程基线

目标：建立可以重复使用和检查的代码工程基础。

| 编号 | 实施事项 | 实施方式 | 验证依据 |
|---|---|---|---|
| E-01 | 确认 Node.js 版本 | 根据最终技术方案确定 | 版本有明确记录 |
| E-02 | 确认 pnpm 版本 | 结合 Node.js 版本确定 | 版本有明确记录 |
| E-03 | 建立 package.json | 根据项目实际需求初始化 | 文件内容与实际工程一致 |
| E-04 | 建立 pnpm-lock.yaml | 使用 pnpm 安装和维护依赖 | 锁文件存在且可正常使用 |
| E-05 | 确定代码语言 | 根据需求和技术决策确定 | 工程配置与实际代码一致 |
| E-06 | 确定代码目录结构 | 根据实际功能和技术栈设计 | 目录结构有明确用途 |
| E-07 | 确定静态检查工具 | 根据语言和技术栈选择 | 检查命令能够执行 |
| E-08 | 确定格式化工具 | 根据项目需要选择 | 格式化规则能够执行 |
| E-09 | 确定测试工具 | 根据实际测试需求选择 | 测试命令能够执行 |
| E-10 | 确定构建工具 | 根据实际技术栈选择 | 构建过程能够执行 |

**注意：**

Node.js 版本、pnpm 版本、语言、框架和工具链尚未确定之前，不应提前编写依赖这些选择的配置。

## 6. 第四阶段：自动化质量控制

目标：将适合自动执行的检查交给 CI。

| 编号 | 实施事项 | 实施方式 | 验证依据 |
|---|---|---|---|
| A-01 | 建立 GitHub Actions 工作流 | 技术栈确定后配置 | 工作流可以正常触发 |
| A-02 | 配置依赖安装检查 | 使用锁文件进行一致性安装 | CI 安装成功 |
| A-03 | 配置静态检查 | 执行项目检查命令 | 检查结果符合预期 |
| A-04 | 配置自动化测试 | 执行项目测试命令 | 测试通过或明确报告失败 |
| A-05 | 配置构建检查 | 执行项目构建命令 | 构建成功 |
| A-06 | 配置 PR 检查要求 | 根据项目实际风险设置 | PR 能展示检查结果 |

**阶段完成条件：**

- CI 可以重复执行项目规定的检查。
- 检查失败能够被发现。
- CI 结果可以作为 PR 的验证证据。
- CI 通过不等于用户验收通过。

## 7. 第五阶段：试运行与改进

目标：通过真实开发任务验证流程是否有效。

| 编号 | 实施事项 | 实施方式 | 验证依据 |
|---|---|---|---|
| T-01 | 选择一个真实需求 | 使用实际项目需求 | 有完整需求记录 |
| T-02 | 执行需求调查 | 由 Cursor 辅助调查，用户确认 | 有调查结论及证据 |
| T-03 | 执行方案设计 | 明确实施范围和技术决策 | 有批准的实施方案 |
| T-04 | 执行代码实现 | 按批准的计划实施 | 代码变更可追溯 |
| T-05 | 执行测试验证 | 按约定的验证方法执行 | 有测试结果 |
| T-06 | 执行交付审查 | 检查 diff、PR 和遗留问题 | 有审查记录 |
| T-07 | 执行用户验收 | 用户根据验收条件确认 | 有验收结论 |
| T-08 | 复盘流程问题 | 记录不适用、重复或缺失的环节 | 有改进记录 |

## 8. 暂不实施事项

以下事项不能仅凭当前项目条件确定：

1. 具体技术栈和框架。
2. Node.js 与 pnpm 的具体版本。
3. 是否采用 pnpm Workspace。
4. 测试框架及测试分层。
5. 静态检查和代码格式化工具。
6. 构建工具。
7. 部署平台及发布流程。
8. 数据库、缓存和外部服务。
9. 安全与性能检查工具。
10. 生产环境运维及监控机制。

这些事项应在真实需求和技术调查之后确定。

## 9. 建议实施顺序

1. 完成 GitHub 项目管理基础。
2. 建立 Cursor 项目规则。
3. 明确项目首个真实需求。
4. 调查并确定技术栈。
5. 建立工程基线。
6. 配置 CI 自动化检查。
7. 使用真实需求完成一次完整开发闭环。
8. 根据试运行结果修订流程规范。

## 10. 最终验收标准

本实施清单全部完成，不代表软件产品已经完成。

流程落地验收应确认：

- 需求管理机制可用。
- 变更管理机制可用。
- Cursor 协作边界明确。
- 代码工程可以重复安装和验证。
- 自动化检查能够正常执行。
- 真实需求可以完整经过调查、设计、实现、验证和验收。
- 重要过程和结果有可追溯证据。

**本清单是 V1.0 流程规范的实施计划，不代表上述配置已经在仓库中完成。**
